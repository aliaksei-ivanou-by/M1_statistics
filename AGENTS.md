# Инструкции для AI-агента

Репозиторий содержит отчеты менеджера по встречам 1-2-1 с сотрудниками. Агент помогает составлять отчеты по присланным материалам и сохраняет их в файлы. Пользователь — менеджер, общение на русском языке.

## Рабочий процесс

1. Пользователь присылает материалы по сотруднику: PDP (personal development plan), заметки или транскрипт встречи, скриншоты формы ввода, устные комментарии. Указывает дату встречи.
2. Агент открывает предыдущий отчет сотрудника и берет из него договоренности. Их статус («Выполнено», «В процессе», «Не выполнено») определяется по присланным материалам или словам пользователя. Если статус неясен, агент спрашивает пользователя и не угадывает.
3. Агент составляет отчет по шаблону `templates/report.md`.
4. Агент сохраняет отчет в `employees/{Familiya_Imya}/{ГГГГ-ММ}.md`:
   - если файла за месяц нет, он создается из `templates/month.md`, затем добавляется блок встречи;
   - если файл есть, новый блок встречи добавляется в хронологическом порядке, а дата добавляется в строку «Встречи в месяце».
5. Агент обновляет сводку `summaries/{ГГГГ-ММ}.md` (создает из `templates/summary.md`, если ее нет): таблицу берет из вывода `.\scripts\summary.ps1 -Month ГГГГ-ММ`, раздел «На что обратить внимание» дописывает сам.
6. Агент обновляет `README.md` — главную страницу с командой и статистикой (см. раздел «README.md» ниже).
7. Агент запускает `.\scripts\summary.ps1 -Check` и убеждается, что блок yaml совпадает с полями отчета. Если PowerShell агенту недоступен (например, агент работает в Linux без `pwsh`), агент составляет таблицу сводки вручную по блокам yaml по формату скрипта и просит пользователя запустить `-Check`.
8. В ответе агент приводит значения всех полей формы в порядке формы ввода, чтобы их можно было скопировать.
9. В конце ответа агент дает команды `git add` и `git commit` для всех измененных файлов. Сам агент не коммитит и не пушит.

## Структура и именование

- Папка сотрудника: `employees/Familiya_Imya`, фамилия и имя латиницей, например `Zakrevsky_Evgeny`, `Mokievets_Darya`.
- Файл месяца: `ГГГГ-ММ.md`, например `2026-10.md`.
- Сводка за месяц: `summaries/ГГГГ-ММ.md`.
- Учет времени за месяц: `timesheets/ГГГГ-ММ.md`.
- Команда и статистика: `README.md`. Инструкция для людей: `GUIDE.md`.
- Заголовок файла: `# 1-2-1: {Фамилия Имя} — {Месяц ГГГГ}`, например `# 1-2-1: Закревский Евгений — Октябрь 2026`.
- Даты внутри файлов всегда в формате `ГГГГ.ММ.ДД`, например `2026.10.23`.

## Учет времени

Пользователь присылает скриншоты таймшитов за месяц. Агент:

1. Заполняет `timesheets/ГГГГ-ММ.md` по шаблону `templates/timesheet.md`. Категории: задача с названием проекта — «На проекте»; IDLE — «Бенч»; Internship — «Стажировка»; Vacation — «Отпуск»; Sick Day — «Больничный». Загрузка = на проекте / (итого − отпуск − больничный), округление до целого процента.
2. Проверяет, что сумма категорий равна итогу по сотруднику на скриншоте, а по дням сверяет периоды (отпуск, больничный, переход на бенч).
3. Выписывает назначения без часов — возможный будущий проект или работа в двух командах.
4. Если сотрудник есть в таймшите, но его строки не раскрыты, ставит «нет данных» и просит пользователя прислать раскрытый скриншот.
5. Сверяет таймшит с отчетами 1-2-1 и README (название проекта, статус проект/бенч, даты) и сообщает пользователю о расхождениях.
6. Обновляет README: колонку «Загрузка», таблицу «Время», при необходимости статус проект/бенч.

Названия проектов берутся из таймшитов. В отчетах 1-2-1 названия проектов не обязательны.

## README.md

README — главная страница: команда и вся статистика. Инструкции в README не пишутся, они в `GUIDE.md` и здесь. После каждого отчета агент обновляет в README:

- строку «Данные на» — дата последних учтенных данных (встречи или конец месяца таймшита) и счетчики сотрудников;
- таблицу «Команда»: проект или бенч, работа в двух командах, дата последней встречи, последние оценки и блокер. Новый сотрудник добавляется в алфавитном порядке;
- таблицу «Оценки 1-2-1» в статистике по месяцам: число встреч, средние оценки по последней встрече каждого сотрудника в месяце (одна цифра после запятой), число сотрудников на бенче, распределение блокеров;
- раздел «На что обратить внимание» — копия из сводки последнего месяца;
- таблицу «Время» и колонку «Загрузка» (см. «Учет времени»);
- таблицу «По месяцам» со ссылками на сводки и учет времени.

## Служебные блоки отчета (не входят в форму)

- **Блок yaml** сразу под заголовком встречи: `date`, `motivation`, `burnout`, `satisfaction`, `blocker`. Значения должны совпадать с полями отчета; при любой правке оценки или блокера менять оба места. Блок используется скриптом `scripts/summary.ps1` для сводок и выгрузки в CSV.
- **Статус прошлых договорённостей:** по одному пункту на строку с префиксом «Выполнено:», «В процессе:» или «Не выполнено:». Невыполненные пункты, которые остаются актуальными, переносятся в новые договоренности. Для первого отчета: «Первый отчёт, предыдущих договорённостей нет.»

## Поля отчета (порядок как в форме ввода)

| Поле | Правило |
|---|---|
| Мотивация | Целое число 1–5 (1 — низкая, 5 — высокая). Без пометок вроде «(предв.)». |
| Выгорание | Целое число 1–5 (1 — признаков нет, 5 — сильное). |
| Удовлетворённость | Целое число 1–5 (1 — низкая, 5 — высокая). |
| Категория блокера | Ровно одно значение: Процессы, Зарплата, Технологии, Команда, Переработки, Нет блокеров. Если блокеров несколько — главный, остальные упомянуть в «Описании проблем». |
| Описание проблем | Коротко, 2–3 предложения связным текстом, без списка. Если проблем нет: «Явных проблем, мешающих работе, нет.» и при необходимости одно-два предложения о рисках. |
| Договорённости (action points) | Обычный текст, один пункт на строку, без маркеров и чекбоксов. Формулировать как действия («Обсудить…», «Уточнить…», «Определить…»), а не как вопросы. |
| Заметки менеджера | 3–5 предложений: сильные стороны, результаты, на что обратить внимание. |
| Отношение сотрудника к double stuff | Если данных нет: «Требует уточнения. Обсудим с сотрудником на встрече в {следующий месяц}.» и добавить пункт «Уточнить отношение к работе в двух командах.» в договоренности. Если сотрудник не на проекте: «Неприменимо: сотрудник сейчас не на проекте.» |

Название поля — именно «double stuff», как в форме ввода.

## Правила содержания

- **Универсальный язык.** Текст должен быть понятен человеку вне проекта: без имен классов, библиотек, внутренних названий модулей и номеров тикетов. Технологии упоминать только на уровне «backend на Go», «unit-тесты», «пользовательский интерфейс».
- **Не упоминать источники.** Не писать «по PDP», «по заметкам», «предварительно», не добавлять поле «Источник».
- **Не выдумывать.** Опираться только на присланные материалы и слова пользователя. Если вывод сделан по косвенным признакам, объяснить это пользователю в чате, но не в отчете.
- **Учитывать только встречи, которые назвал пользователь.** Если пользователь просит убрать встречу, убрать ее и из строки «Встречи в месяце».
- **Нейтральный и уважительный тон.** Без оценочных ярлыков; риски формулировать как риски («может привести к…», «стоит проследить…»).
- **Сотрудник/сотрудница** — согласовывать род по сотруднику.
- Если несколько сотрудников работали на одном проекте, общие проблемы можно описывать одинаково, а заметки и договоренности — по роли каждого.

## Как выставлять оценки

- Опираться на конкретные сигналы: выполнение плана, инициативу, рост ответственности (мотивация); объем и разнородность задач, переработки, больничные, нехватку времени на развитие (выгорание); соответствие задач интересам, ясность перспектив, наличие проекта (удовлетворенность).
- Сотрудник без проекта (поиск проекта, собеседования): как правило, категория блокера «Процессы», удовлетворенность не выше 3.
- После выставления оценок кратко объяснить пользователю в чате, почему выбраны именно такие, если оценка неочевидна.

## Чего не делать

- Не коммитить, не пушить и не удалять файлы без явной просьбы.
- Не менять оценки и формулировки, которые пользователь уже утвердил или ввел в форму, без его просьбы.
- Не сохранять в репозиторий исходные материалы (PDP, транскрипты) — в нем только итоговые отчеты.
- Не менять кодировку `scripts/summary.ps1`: файл должен оставаться в UTF-8 с BOM.
